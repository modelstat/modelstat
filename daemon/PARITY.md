# Parity decisions — the Rust daemon vs the retired TypeScript daemon

The rewrite had to stay byte-for-byte compatible on ids, device identity, wire
schemas, and the redaction floor (session task rules; feature §21, plan §4).
That port is complete and the TypeScript daemon is deleted, so the rows below
are now the RECORD of why the Rust behaves as it does — every one of them is a
frozen commitment, not a diff against a live sibling. Devices, SDKs and the
server all still depend on these choices; change one only with a migration.

The surviving TypeScript is `packages/core` (the wire/redaction reference the
golden fixtures are generated from) plus the segmentation pipeline in
`packages/daemon-core` that the Chrome extension ships, and it is still held
byte-identical to `modelstat-wire` by the golden fixtures. Add a row here (and, for intentional
divergences, a line in feature §23) rather than leaving a silent choice.

## Faithful ports (behavior identical, implementation adapted)

| Area | Decision |
|---|---|
| **djb2-64** (`evt_`/`seg_`/`tc_` ids) | Hash over **UTF-16 code units** (`str::encode_utf16`), matching JS `charCodeAt` — not bytes or code points. `h.wrapping_mul(33) ^ (unit as u64)` equals JS's `(h*33)^c` masked to 64 bits (AND distributes over XOR). base36 matches `BigInt.toString(36)` (lowercase, `"0"` for zero). |
| **Device UUIDv5** | `SHA-1(namespace_bytes ++ utf8(machineKeyHex))`, version/variant forced. The salt path (`MODELSTAT_DEVICE_SALT`) hashes `"<key>:<salt>"`, exactly as TS `intendedDeviceUuid`. |
| **Machine-key hash** | `SHA-256("modelstat.device.machine-key.v1:" + raw)`. The salt const is frozen (feature §18); it is not exported from the TS, so it is replicated verbatim and the fixture generator computes the golden with the same literal. |
| **paramShape** | Splits on exactly `[ \t\n\r\f]+` (NOT the full Unicode `\s`, and NOT vertical tab), matching the JS regex character class. |
| **Enums** | Carried as validated `String`s, not Rust enums (the sets are large/churny and the daemon must round-trip a value a newer server knows). `enums.json` pins order+membership against the TS arrays. |
| **Byte clamp** | `clamp_utf8_bytes` iterates code points (`chars()`), matching JS `for…of`; astral chars kept/dropped atomically. Drives off declared caps, not a hand-listed field set (the field-by-field version shipped the CJK-400 bug). |
| **Redaction floor** | `regex` crate with `(?-u:\b)` for ASCII word boundaries and ASCII classes spelled out (`\d`→`0-9`, `\w`→`A-Za-z0-9_`) to match JS semantics. The wire floor replaces the **whole match** with `[REDACTED:<name>]` (the catalogue's replacement templates are for the SDK-side redactor, ported in M3). |
| **`aws_secret_key`** | JS uses lookaround (`(?<!…){40}(?!…)`) the `regex` crate can't express. Implemented as an exact-length run scan — provably equivalent (a lookaround-bounded run matches iff a maximal class run is exactly 40 chars). |
| **Entropy pass** | Shannon entropy sums floats in **first-occurrence order** (JS `Map` insertion order) so the running total is bit-identical and a threshold decision can't flip on float non-associativity. Candidates are pure ASCII, so `chars().count()` == JS `s.length`. |

## Intentional additions / divergences (also noted in feature §23 where applicable)

| Area | Decision | Why it's safe |
|---|---|---|
| **Agent enum count** | Spec §4 prose says "34-enum"; the TS `AGENTS` array has **33**. Rust matches the **code** (33), per the spec's own "code wins" rule (§23). | Fixture `enums.json` is generated from the TS array, so the two can't disagree. |
| **Windows redaction paths** | `C:\Users\…`, `%USERPROFILE%`, and UNC `\\host\share` are redacted (feature §17.4 mandates them; the TS had none). No TS golden exists, so they're covered by Rust-only unit tests in `paths.rs`. | Additive (strictly more privacy); lands under PROCESSING_VERSION 16; doesn't affect the TS-derived redaction goldens (which contain no Windows paths). |
| **`references` / `session_metadata` (wire)** | The wire `RawEvent.references` + `IngestBatch.session_metadata` fields stay opaque `serde_json::Value`; the typed model + fold now live in `modelstat-parsers::references` (M4 §7.4) and are serialized to `Value` only at batch assembly. | Lossless round-trip on the wire; the typed structs match the TS field order so the serialized `Value` is byte-faithful. See the M4 section for the port. |
| **`state.json.selfHostedModel`** | Not a field on the Rust `state` struct — read-tolerated, ignored, dropped on next write (feature §19). | The legacy-state golden (`file_formats/state_legacy.json`) carries it so the M1 reader is tested against it. |
| **Per-file cursor = a send floor, not just a change flag** | The TS re-ships **every** event of any file whose size/tail changed. Rust still parses the changed file WHOLE, but only buffers events at/past the cursor's byte offset (`shipped_below`, `scan.rs`). | The TS behaviour re-summarised and re-uploaded an entire live transcript on every append: a 67 MB / 17,582-line session shipped 17,582 events per cycle where 61 were new, so the daemon never left `uploading` and the tray sat on a constant "Uploading 1000 events". Parsing stays whole, so the cross-line state a mid-file start would lose (model attribution, `tool_use` ↔ `tool_result` pairing) is untouched, and `source_event_id`s are unchanged — the server sees exactly the same events, once instead of every cycle. The floor is taken **only** on in-place growth (`cs.size >= cur.size`); a truncated/rewritten file's offsets are meaningless so it re-ships whole, and the eager force scan (`force_read_all`) never takes one. Tool-call drafts are deliberately un-floored — a draft is completed in place when its `tool_result` pairs, which can land scans later. An empty flush now still advances pending cursors, or a grown-but-nothing-new file would re-parse forever. |

## M1 — identity, config, device API (structural + behavioral decisions)

| Area | Decision | Why it's safe / faithful |
|---|---|---|
| **Foundation crate placement** | paths, machine-key probes, the identity + state stores, `Config`, and the device-API client all live in **`modelstat-ingest`**, not `modelstat-daemon`. | Forced by the frozen dep graph: `recoverIdentity` is spec-assigned to `modelstat-ingest` (plan §3) and needs config + identity; `modelstat-daemon` *depends on* `modelstat-ingest`, so the foundation can't live in daemon without a cycle; `modelstat-wire` is pure-contract (no I/O). `ingest` is the lowest I/O crate below both `daemon` and `cli`. The M0 `device.rs` comment guessing "M1 (`modelstat-daemon`)" is superseded by the graph. |
| **`Config` = explicit struct** | The TS module-level singleton `state` (cached identity + module-level recover backoff) is modeled as a `Config` you construct and pass, identity behind a `Mutex`; the recover backoff lives on the `DeviceApi` instance. | Behaviour is identical — write-through setters, same api-url resolution order, same `[0,2,5,15,30,60]s` recover schedule. The struct makes the five e2e scenarios drivable in one process and keeps env-dependent state out of process globals. |
| **machine-key fallback honors `MODELSTAT_HOME`** | The fallback key file is `home_path("machine-key")`, not a hard-coded `~/.modelstat/machine-key`. | The one intentional §23 fix. Hardware-id devices (the vast majority) are unaffected; only a fallback-key device that *relocated* may re-derive (documented, acceptable). Unit-tested via `fallback_key_file_honors_modelstat_home`. |
| **`os_family` gains `windows`** | `build_fingerprint` maps Windows → `"windows"`; the TS returned `"other"`. | Feature §4 mandates it and `OS_FAMILIES` (in `modelstat-wire`) already carries `"windows"`. Additive; the server enum accepts it. |
| **`os_version`** | `uname -r` on Unix (byte-identical to Node `os.release()` on macOS/Linux); `cmd /c ver` parse on Windows. | Not a golden-tested value (inherently machine-specific); the server just stores/displays it. Windows service specifics land in M5. |
| **self-hosted URL override** | `MODELSTAT_SUMMARIZER_URL` overrides the stored URL; the `MODELSTAT_LLM_*` family is gone. | Feature §19/§23 (BYO endpoints dropped, one env var replaces the pair). |
| **`--fresh` convergence** | Proven by the `e2e_m1` integration test and `scripts/e2e-m1.sh` via *back up + wipe identity + re-register* — the exact machine-stable path (feature §21.9). The `connect --fresh` **command** lands in M6. | The convergence mechanism (derive same uuid → dedupe on `machine_id` → same `device_id`) is M1 and fully exercised; only the `connect` wrapper is deferred. Staying inside the milestone boundary. |
| **Fake device-API server** | The e2e is proven against an in-process axum fake server (dev-dependency only — never linked into the collector) that reproduces the real server's `{data:…}` envelope + `machine_id` dedupe (verified against `core/rust/crates/api/src/devices.rs`). | Docker isn't available here to stand up the real Postgres/ClickHouse/MinIO + API stack; plan §6 explicitly sanctions a "fake … server harness". `scripts/e2e-m1.sh` runs the same flows against a real `$DAEMON_API_URL` when one is provided. |
| **`token` / prod-guard copy** | `token` unpaired hint and the prod-guard "run it interactively" remedy say `modelstat`, not the TS `npx modelstat@latest`. | The npm path is dropped (§22); the binary is `modelstat`. Not a golden-tested string (stderr help text); the AC checks the **exit code** (1 / 2). |
| **`cli/status.json` api-vs-dashboard note (not M1)** | The M0 `status.json` golden pairs `api: api.modelstat.ai` with `dashboard: modelstat.ai/dashboard`, which is inconsistent with the TS `dashboard = <apiUrl>/dashboard` derivation. | Flagged here for **M5** (the `status` command) to resolve deliberately. M1 keeps `DEFAULT_API_URL = https://modelstat.ai` (TS parity); the `paths`/`token` `api` field is just `state.apiUrl`. |

## M2 — parsers, discovery, tool-action (structural + behavioral decisions)

| Area | Decision | Why it's safe / faithful |
|---|---|---|
| **`serde_json` `preserve_order`** (workspace) | Enabled so `Value` objects serialize in insertion order, not sorted. | `args_hash` = sha256 over the tool input exactly as `JSON.stringify` emits it (source-key order); a `Value` re-serialized with sorted keys would hash differently. Only affects `serde_json::Value`; struct-field `BTreeMap`s are unchanged. Side effect: the Rust-emitted `references` blob now matches the TS field order `{repos, pull_requests, issues}` — it previously serialized sorted (`{issues,…}`), a latent mismatch this fixes. |
| **Byte offsets** | Each line advances `utf8_len(line_without_newline) + 1`; `source_byte_offset` captured before the advance (`line_reader.rs`). | Byte-exact vs the TS `Buffer.byteLength(line)+1` on LF files (every fixture); on CRLF it drifts identically to the TS, so `source_event_id` matches either way. |
| **Resume-copy dedupe** | `AncestorCache` does the same-dir probe then a one-level sibling-dir walk under the projects root, memoised. A line whose `sessionId` ≠ the filename uuid is dropped when the ancestor `<sid>.jsonl` exists; else emitted keyed by `uuid::<lineUuid>`. | Byte-for-byte port of `dedupeIdFor`/`ancestorFileExists`; the `claude_synthetic` (all lines dropped) + `claude_resume_copy` goldens exercise both paths. |
| **codex `event_msg` timestamp** | TS falls back to `new Date().toISOString()` when a line has no `timestamp`; the Rust port falls back to the last-seen line timestamp instead (else skips the event). | Determinism > wall-clock (a replayed scan must re-derive identical ids/ts); codex always writes timestamps, so this never differs in practice. Noted as an intentional §23-class divergence. |
| **Turn timing is read from the source, never derived** | Three divergences from the TS line, all in service of the same primitive — the instant and the turn a message belongs to. (1) `claude_code` requires a `user`/`assistant` line to STATE a `timestamp`; the TS shipped `ts: ""` for one that did not, which parses as epoch 0. The line is now counted in the skip ledger instead. (2) `claude_code`'s stated duration is read by shape (`stated_duration_ms`), not from the single key `toolUseResult.durationMs`; Claude Code writes `durationMs`, `durationSeconds` and `totalDurationMs` across three tools of one release. (3) `codex`'s `turn_index` advances at a typed prompt (`event_msg`/`user_message`), where the TS advanced it at each usage-bearing `token_count` — an API round trip. | The server derives every wait from message timestamps and groups by `turn_index`, so both fields must mean ONE thing across agents. The codex reading was the outlier: a single-prompt fixture spanned turns 0, 1 and 2. A stated duration is the agent's own measurement and unrecoverable off-device, so it is passed through wherever a record states one — including records no parser arm models. Covered by `every_real_fixture_dates_every_event_and_numbers_turns_by_the_prompt` and the regenerated `codex_basic` golden. |
| **Cursor snapshot** | Opens a byte-snapshot COPY of the `.vscdb` read-only via `rusqlite` `bundled` (read → temp → open), never the live file (plan D6). Walked on every scan since daemon 1.7.0; reads the real chat store (`cursorDiskKV` bubbles) rather than the long-gone `ai_code_hashes` table. | Static-linked SQLite; snapshot avoids locking a DB Cursor holds open. `sql.js` (WASM) is dropped — a Node runtime dep the collector can't have. |
| **`references` mining** | `detectReferences`/`detectEventReferences` are ported into `modelstat-parsers::references` (the parsers call them at parse time), producing an opaque `serde_json::Value` on `RawEvent.references`. The rest of `core/session-metadata.ts` (typed `SessionMetadata`, `dedupeSessionMetadata`, `detectBranchTickets`, `dedupeFiles`) + the git-outcome/`--numstat` enrichment land in M4 (see that section). | The parser must not silently never-detect references (that would be a stub); the miner is pure + tested. Modeling the output as a `Value` matches the wire schema's passthrough decision (row above). |
| **Regex ASCII classes** | `\w`/`\d`/`\b`/`\s` spelled out as ASCII (`[0-9A-Za-z_]`, `(?-u:\b)`, …) since Rust's `regex` is Unicode-by-default while JS's are ASCII; a literal `[` inside a character class is escaped (`\[`) because Rust reads a bare `[` as a nested-class opener. | Matches JS regex semantics exactly (the `regex` crate has no direct `\b`-ASCII shorthand). |
| **`normalize_tool_name` cap** | Truncates to 120 **UTF-16 code units** (JS `String.slice`), not bytes/code points, via `slice_utf16`. | Faithful to JS; BMP-only tool names (the universe) slice identically to a char count. |
| **Fixture reconstruction** | The parser golden test rebuilds the exact `/tmp/modelstat-fixtures` tree (committed under `tests/fixtures/tree/`) and parses at those canonical paths; `#[cfg(unix)]`. | `source_event_id` embeds the `/tmp/modelstat-fixtures/...` path, so parity requires the generator's documented fixed base path; Windows offset/path parity is out of scope for the golden suite (the generator runs on Linux/macOS). |
| **Discovery: app-registry dropped** | The macOS `system_profiler` strategy + all `bundleIds` matching are removed (feature §22). | The TS `macosListApps` always returned `bundleId: ""`, so the `find(a => a.bundleId === bid)` never matched — dead code. |
| **Discovery: Windows support added** | An `Os::Windows` arm with `%APPDATA%`-based GUI data dirs + PATH/`%LOCALAPPDATA%\Programs`/scoop/winget binary dirs (§7.2). The TS only branched macos/linux. | Additive; the daemon is headless on Windows but still discovers installs/identities. No golden (env-probing output is machine-specific). |
| **Discovery: identity probes** | Claude keychain (`security`), `~/.claude.json` `oauthAccount`, Codex `auth.json` JWT (hand-rolled base64url decode, dependency-free), Gemini `oauth_creds.json`, Cursor `storage.json` `cursorAuth/*` — all best-effort. | Byte-faithful to the TS probe order + stable-id derivation; the pure helpers (`classify_install_method`, JWT decode, dedupe) are unit-tested. |

## M4 — session→batch builder (structural + behavioral decisions)

| Area | Decision | Why it's safe / faithful |
|---|---|---|
| **`batchId` placement + entropy** | The inline ULID (`core/ids.ts`) ports to **`modelstat-pipeline::batch::ulid`/`batch_id`** (with `attach_segment_ids` + `prepare_cloud_raw_events`), not `modelstat-wire::ids`, adding a `getrandom` dep to pipeline. | Wire stays a pure deterministic contract (no clock/entropy); the batch id is random (nothing pins it) and lives with the batch-assembly it serves. The TS variant — 10 base32 time chars + 16 chars of `byte % 32` — is reproduced exactly (shape, not value). |
| **Cloud raw redaction fail-closed** | `prepare_cloud_raw_events` returns `None` when `ner_active` is false — the caller then keeps data local rather than shipping floor-only turns. Tool-call `command_redacted` gets the NER pass too (deduped per command). | Byte-faithful to `prepareCloudRawEvents`'s `if (!nerActive) return null`; the fail-closed gate is the §9.5/§21.5 egress contract (never ship less-redacted). The unchanged-excerpt identity check (`scrubbed === original` → keep the event) matches too. |
| **Tool-call attribution** | `attach_segment_ids` builds the `source_event_id → segment_id` map from the batch's segments; `attach_segment_ids_by_map` takes a prebuilt owned-string index so the scan loop can accumulate it across flush boundaries (straddling calls stay attributed instead of dropping to null). | Direct port of `attachSegmentIds`/`attachSegmentIdsByMap`; `ToolCallDraft → ToolCallWire` is a field-for-field copy + the resolved `segment_id` (`?? null`). |
| **Session-metadata pass placement** | `buildSessionMetadata` (`daemon-core/pipeline/session-metadata.ts`) ports to **`modelstat-pipeline::session_metadata`** (next to `build_session_titles`), so `modelstat-pipeline` gains a dep on the `modelstat-parsers` sibling. The pure fold (`dedupeSessionMetadata`, `detectBranchTickets`, `dedupeFiles`, typed `SessionMetadata`/`FileRef`) ports into `modelstat-parsers::references` (extending the M2 reference core). | The pass needs the titler's `sample_abstracts`/`strip_cognition_suffix` (pipeline) **and** the reference core + git reads (parsers); pipeline→parsers is a clean one-way edge (parsers has no llama and doesn't depend on pipeline). The engine binary doesn't link pipeline, so no bloat there. |
| **Git enrichment = one injected trait** | The TS `opts.{resolveGit,checkPrOutcome,collectFilesChanged}` (three independent optional closures) become one `GitEnrichment` trait (`modelstat-parsers::git_enrich`) with a `RealGitEnrichment` impl fronting the cached `GitResolver` + the two stateless git-history reads. `None` disables all git channels. | "Absent" and "present-but-returns-`None`" are observationally identical to the pass, so one trait covers the whole TS optionality space; a test fake implements only what it needs. Keeps the git subprocess out of the pipeline (pure + unit-testable). |
| **Link-extract model = injected async trait object** | The `opts.extractLinks` model call is a `LinkExtractor` boxed-future trait object injected into the pass; the frozen prompt lives in `pipeline::prompts` (`LINK_EXTRACT_SYSTEM_PROMPT` + `build_link_extract_user_prompt`, already transcribed). | The pipeline never links the engine directly (same seam as the resilient summarizer); the collector builds the closure from the prompt + summarizer client. Best-effort — a `None` reply just leaves the deterministic channels standing. |
| **PR outcome fields** | `PullRequestRef` gains `merged: Option<bool>`, `merged_at: Option<Option<String>>`, `reverted: Option<bool>`, all `skip_serializing_if = "None"`. Unenriched PRs (incl. every `RawEvent.references` blob) omit them entirely; an enriched-but-unmerged PR serializes `merged:false, merged_at:null, reverted:false`. | Matches the TS zod `.optional()` (absent) vs enrichment writing an explicit `null` `merged_at`. The nested `Option<Option<…>>` is what distinguishes "absent" from "present-null". Event-reference goldens are unaffected (fields always absent there). |
| **Unparseable `until` → keep, don't drop** | If the session window's `until` timestamp can't be parsed to ms, the files step is skipped but the metadata found so far is kept. TS would throw in `new Date(NaN).toISOString()` and the per-session `try/catch` would drop the WHOLE session's metadata. | The timestamps are always valid ISO from our parsers, so this never fires in practice; where it theoretically could, keeping the deterministic metadata is strictly better than silently dropping it (no-silent-data-loss). |
| **Output map ordering** | `build_session_metadata` returns a `BTreeMap` (sorted session ids); TS returns a `Record` in first-seen insertion order. | Per-session values are independent of iteration order (the git cache is a pure `cwd→context` function), and the server does key lookups — order is not semantic. No golden pins `session_metadata` (the batch golden has it absent), so this is free. Consistent with `build_session_titles`. |
| **Scan hold vs throw** | `run_scan_over_jobs` returns `ScanTallies { held: bool, .. }` and STOPS the scan on a held flush; the TS `commitBatch`/`uploadBatch` THROWS on any non-commit and the exception unwinds out of `runScanOverJobs`. Both leave the buffered files' cursors un-advanced → same events re-ship next cycle. | Same never-drop outcome, expressed as a value not a panic (the Rust daemon must not crash on routine engine-down/offline — see the no-degrade principle). `held` also lets the daemon distinguish "held, wait for recovery" from `more_pending` ("cap hit, re-scan now"); the TS conflated both into a thrown scan. |
| **Hold carries a SCOPE** | `upload_batch` returns `UploadResult::Hold { reason, scope }`, and the spool drain STOPS the pass only for `HoldScope::Wire` (network/5xx/429/408/auth). A `HoldScope::Batch` hold (the server answered 400/413/415/422 — it rejects THIS payload) is counted, logged as an error, and the pass keeps going. The TS uploader has one undifferentiated failure and stops everything. | Still never-drop: the file stays spooled and is retried, exactly as before. What changes is only whether SIBLINGS get their turn. Without the split, one permanently-rejected batch at the head of a FIFO spool is a total ingest outage for that device — a live incident where an unmodelled OMP record kind (`thinking_level_change`) held 98 batches for 14 hours while the daemon reported "scanning". The count is published as the `batches_refused` stat so `modelstat status`, the tray and the heartbeat can never again say "idle" through it. |
| **Skip-check = size + tail only** | A file is skipped as unchanged when `cursor.size == cs.size && cursor.tail_hash == cs.tail_hash` — `mtime` is deliberately NOT compared (a touch that didn't change bytes re-uses the cursor). | Byte-faithful to `scan.ts:656` (`cur.size === cs.size && cur.tailHash === cs.tailHash`). The `FileCursor` still carries `mtime` for the wire/state golden, it's just not part of the equality. |
| **Injected seams + two git resolvers** | Everything the loop touches I/O with is an injected closure/trait (`parse`, `checksum`, `correct_events`, `enrich_scripts`, `BatchUploader`, `CursorStore`). Authoritative-git CORRECTION (`correct_events`, over its own resolver) is kept separate from the METADATA git (`git: &mut GitEnrichment`, lent per-flush). | TS closes over module singletons (`state`, `uploadBatch`, boot-time adapters); Rust makes them parameters so the whole state machine is unit-testable against a fake engine + fake server (7 tests, no real `.jsonl`/network). Two resolver instances = two caches — cheaper than threading one `&mut` through two borrow points, and correctness-neutral (a resolver is a pure `cwd→context` cache). |
| **Per-push flush = exact-size batches** | Events push one-at-a-time with the `>= BATCH_MAX_EVENTS` check after each, so every batch is exactly `BATCH_MAX_EVENTS` except the trailing one; a file's events straddling a boundary advance the file's cursor only after the LAST batch carrying them. | Reproduces the TS streaming `sink` (per-event `if (buffer.length >= BATCH_MAX_EVENTS) await flushBatch()`) even though the Rust `parse_job` collects the whole file — same batch boundaries, same straddle-cursor semantics (verified by the 1100-event test). `BATCH_BUFFER_HARD_CAP` is a `debug_assert` (unreachable by construction) rather than the TS runtime throw. |
| **Reconcile seams + typed state** | `reconcile_backfill` takes the digest tree (`BackfillDigest`), the local state (`ReconcileStore` over `RuntimeState`), and `list_files`/`parse_counts`/`request_scan` as injected seams; the cache + backoff map are typed structs (`DigestEntry{mtime, perDaySession}`, `ReshipRec{attempts, lastAt}`) serialized to/from the `reconcile_cache` / `reship_state` `Value` fields. | Same testability rationale as the scan loop (7 fake-driven tests, no server / real transcripts). The camelCase field renames keep the persisted `state.json` shape identical; the golden pins both fields as `{}` (empty), which round-trips unchanged, and populated entries are internal (not golden-pinned). |
| **Backoff shift overflow-safe** | The re-ship backoff `RESHIP_BACKOFF_BASE_MS * 2^(attempts-1)` caps the shift at 32 (`(attempts-1).min(32)`) and uses `saturating_mul` before `.min(MAX)`. | JS computes this in f64 (a huge `attempts` → `Infinity`, then `min(Infinity, MAX) = MAX`); Rust i64 would overflow-panic. Capping the shift is behaviourally identical (for any `attempts ≥ 6` the value already exceeds `MAX`, so the `.min` returns `MAX` either way). The `attempts > 0` guard keeps `attempts - 1` from underflowing. |
| **`(day, session)` key + map ordering** | The backoff key is `format!("{day}\0{sid}")` (embedded NUL, as in TS); the rollup/day/session containers are `BTreeMap`/`BTreeSet` (sorted) where TS uses `Map`/`Set` (insertion order). | The NUL key round-trips through JSON as `\u0000` (byte-faithful to the TS state). All reconcile outputs (`days_checked`, `sessions_short`, the re-ship file set) are counts or sets — independent of iteration order — so sorting is free. |
| **`FileQueueStore` untyped snapshot `items`** | The read-target's `items` is `Option<serde_json::Map<String, Value>>` (untyped); only after the `version == 2` gate is each row deserialized into a typed `QueueItem`, tolerantly (a row that fails is skipped, not fatal). | A strict `Map<String, QueueItem>` would make a valid-JSON **v1** snapshot (its rows carry the old `tool` key, missing `agent`) a whole-file deserialize ERROR → the corrupt-JSON `.bak` fallback. The untyped layer reproduces the TS exactly: `JSON.parse` succeeds, then `version === 2` fails → dropped wholesale to an empty map. The `.bak` fallback then fires only on genuinely invalid JSON / a read error (as in the TS `catch`). |
| **`FileQueueStore` sync-under-async + BTreeMap** | The `QueueStore` methods are `async fn` (the TS contract the receiver awaits) but run fully synchronously over a `std::sync::Mutex` + `std::fs` (no await inside the lock, so the guard never crosses a suspension point). `items` is a `BTreeMap` (deterministic snapshot) vs the TS `Map`. | The queue files are a few KB, so sync I/O under a held lock is simpler + crash-safer than the TS promise-chain write serialization and identical in effect (one writer at a time). The atomic write (`.tmp` → rotate current to `.bak` → promote `.tmp`) and the `${path}.bak`/`.tmp` sibling naming are byte-faithful; the sorted map only makes the on-disk key order deterministic (a JSON object's key order is not semantic). |
| **`build_batches` PipelineRunner can HOLD** | The `PipelineRunner::run` seam returns `Option<Vec<Segment>>` (`None` = engine unavailable), and any held session makes `build_batches` return `DrainBatches::Held` — nothing ships, the events stay queued and retry. The TS `buildBatches` has no hold: `pipeline.run` returns `Segment[]` and (pre-rewrite) degraded to extractive segments when the engine was down. | The no-degrade override (superseding feature §9.4): the SDK-drain path must HOLD like the file-scan path's `build_flush_batches`, never ship a degraded batch. Structurally identical otherwise — same per-session debounce (`SESSION_DEBOUNCE_MS`=7000 / `FORCE_SHIP_THRESHOLD`=200), same split-before-cap, same `batch_id` + `attach_segment_ids`. `finalise` groups its events by session with a `BTreeMap` (sorted) vs the TS `Map` (insertion order); the per-session pipeline runs are independent and segments are keyed by id server-side, so the segment array's order is not semantic (no golden pins the queue-path batch). |
| **`parse_batch` stricter than TS** | `parse_batch` deserializes the body into a typed `WireBatch`, so serde requires all 6 non-optional `RawEvent` fields (`source_event_id`/`ts`/`kind`/`agent`/`provider`/`session_id`); the TS `parseBatch` only checks 4 are non-empty strings and passes the untyped object through. The empty-string check on the 4 TS-checked fields is kept on top. | The SDK always sends `kind`/`provider` (they're core `RawEvent`), so this never diverges in practice, and a genuinely-malformed event (missing `kind`) is better rejected `400` here than queued and later rejected by the backend. `event_ts_ms` reproduces `Date.parse(ts) || Date.now()` including the JS falsy-`0` edge (an exact-epoch ts falls back to now). |
| **Receiver server: control runner + allowlist** | `ControlScanHandler` is a boxed-future closure (`Arc<dyn Fn(..) -> Pin<Box<dyn Future>>>`, like the pipeline's `LinkExtractor`) so the axum server stays a concrete non-generic type; `ControlRunner` serializes runs with a `tokio::sync::Mutex` — CHAINING every target (a requested session always runs), matching `createControlRunner`, NOT the coalesce-drop `CoalescingRunner`. `is_allowed_transcript_file` lexically resolves `.`/`..` (a hand-rolled `Component` fold, NOT `std::fs::canonicalize` which needs the file to exist) then checks component-wise `Path::starts_with` (so `/a/bc` doesn't match root `/a/b`). | Node's `resolve()` is lexical (no stat) + `startsWith(root + sep)` is a separator-bounded string prefix; the `Component` fold + `Path::starts_with` reproduce both exactly and still work for a brand-new file mid-write. Wrong-METHOD requests get axum's default `405` where the TS returned `404` (unknown *paths* still 404 via the fallback) — a cosmetic divergence the SDK never hits. |
